# GFN-17 benchmark observations

These data describe proof-producing searches on one Ryzen 5 7600 workstation running Ubuntu and NVIDIA driver 595.99.02. All times in the CSV files are UTC. Run `python3 reproduce.py` in this directory to rebuild the hourly and nine-hour counts, calculate paired throughput and time ratios, and check the proof manifest with the Python standard library. Each CSV row links to its original measurement. The CSV files include the fields needed for these calculations and can be used offline.

## Production measurements

| File | Observation |
|---|---|
| `production_intervals.csv` | 54 adjacent telemetry intervals from 04:30:01 through 13:30:01 on 21 November 2026, with a row for each of four devices per interval. Each source link identifies an immutable telemetry snapshot. |
| `production_windows.csv` | Nine adjacent one-hour windows derived from the shorter per-device counts. The fleet totals match each snapshot's independently tabulated 60-minute counter. |
| `deployment_trials.csv` | Four earlier deployment windows A–D, one hour per window. Counts, per-device concurrency, and certificate-slot seconds accompany the median duration of searches fully contained in each window. |
| `validation_snapshots.csv` | Asynchronous project-side queries for A–D. The rows give the scope, observation time and classification of each cohort. Repeated observations cover overlapping sets of results. |

The host counts the first successful terminal log record per BOINC result name across all four services. It uses half-open time intervals. A main search and a certificate have distinct result-name suffixes. The public validation status can change long after local completion. The nine-hour data have full local coverage of the four services with a stable selected profile on every device. They measure one uninterrupted period after D. A server-status join for those 1,838 searches is unavailable here. The attached `source` links on the short intervals identify all four per-device records. The links on the hourly rows identify the independent fleet check at the end of the hour. [Counter implementation](https://github.com/ricardofitas/prime-grid-comm/blob/8716ffe56f8888494c9379e64735c6929561dcef/benchmarks/boinc/boinc_counts.py)

The deployment windows used the default 0.2 software on all four cards for A and B. Relative to A, B increased the RTX 4060 fan setting to 85%. C selected the three-prime `small32` arithmetic profile on the RTX 2080 Ti. D returned the RTX 4060 fan setting to automatic and selected eight centered residue channels with exact carry on that card. The RTX 4060 Ti and RTX 3070 retained their 0.2 selections. Job arrivals and certificate workloads differed. The online comparisons have one hour per configuration and no randomized assignment. The file preserves the median across searches that both began and ended within each period. Counts include all searches that finished within each period. [Deployment report](https://github.com/ricardofitas/prime-grid-comm/blob/8716ffe56f8888494c9379e64735c6929561dcef/reports/ciclos/vibefer2-2026-11-21-ensaios-4060.md)

## Matched timings and arithmetic checks

| File | Observation |
|---|---|
| `matched_runs.csv` | Search and batch wall times with the configuration and workload attached. Historical eight-base RTX 4060 Ti runs, individual graph/leaf tests, three- and four-card replays, and the separate 32-search batch have distinct experiment IDs. |
| `kernel_controls.csv` | Graph-dispatch and one- versus two-worker timings on the Gen3 ×1 RTX 3070, and three third-channel arithmetic controls on the RTX 4060 Ti. |
| `ti_third_channel.csv` | Six complete permutations of the stock, alternate-integer, and FP32 third-channel variants on the Ti. Includes the timing and worker overlap from each arm. |
| `ti_layout_check.json` | Calibration of the Ti's captured three-prime leaf input/output layout, buffer SHA-256 digests, residue counts and immutable evidence locations. Six real checkpoint inputs and one edge-case input entered the isolated leaf checks. |
| `profile_proofs.csv` | Seven complete offline proof comparisons. Three eight-channel RTX 4060 proofs matched their official files. The RTX 2080 Ti generated two proofs with small32 and two with its control on the same two bases. Keys refer to each archived challenge. |
| `paired_squares.csv` | Three overlapping workers on an RTX 4060, each running 131,072 dependent squarings from its checkpoint. Each carry series contains all six permutations of stock, centered-eight and centered-nine. The 8,192-step warm-ups are excluded. |
| `ti_alternatives.csv` | RTX 4060 Ti complete dependent squarings on six simultaneous workers with a 33% MPS quota, 65,536 squarings per worker. The boundary alternative varies the number of columns (16 or 32). The cuPQC leaf varies threads per block (128 or 256). The file retains all eight measured pairs for each setting. |
| `proof_manifest.csv` | All 32 candidate bases in the isolated four-card replay, mapped to devices with proof digests, sizes, residues, and keys. Genefer22 completed both server and certificate stages on each. An official proof file was available for eight of the bases and matched byte-for-byte in each case. The manifest records digests. The proof binaries require a new computation or access to the original files. |

In the RTX 4060 timing study, the aggregate time per squaring is the shared wall interval across concurrent workers divided by the total number of candidate-squarings. For each block, divide the stock time by the candidate time to get a throughput ratio. Report the median of the six ratios. For the RTX 4060 Ti comparisons, the reported percentage is the median of the within-pair *time* ratios minus one, expressed as a percentage. The regulators and concurrent workers can make successive measurements dependent. The summaries describe the measured cases without distributional assumptions.

Each matched-run rate uses the count of completed candidates divided by the shared wall time. The eight-base Genefer26 entry uses a depth-six vector proof. The other entries in that comparison use individual proofs. The original Vibefer and Vibefer2 0.1 are distinct executables. The single-base graph experiment uses the same base and PCIe Gen3 ×1 RTX 3070 throughout. The three-to-four-card experiment also changes the work distribution and includes a PCIe recabling, so its timing incorporates those changes. In the 32-candidate batch, startup and the time until the final client exits enter the denominator. Subsequent independent verification has its own timing. Replaying the bases produces no new project credit.
